# Daybook M3: Editing Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Events can be read in full, created, edited and deleted, including recurring series ("only this event" or "this and future events"); calendars can be created and recoloured. Every write refreshes the views once, without a flicker.

**Architecture:** The write side of `CalendarStore` and every value it needs live in `Packages/DaybookCore`: `EventDraft` (editable fields, validation, default for a new event, keeping the duration when the start moves, time zone changes), `RecurrenceRule`, `AlertOffset`, `Attendee`, `SourceInfo`, `CalendarDraft`, `EditSpan`, `CalendarStoreError`, the preset calendar colours with their contrast check, and the time-grid slot snapping. `InMemoryCalendarStore` implements every write, including recurring series expanded into occurrences, with exceptions for single occurrences and splitting for "this and future". `App/System/EventKitCalendarStore.swift` translates the same operations to EventKit and stays thin. `AppModel` stays the single owner of state and performs the writes; the form state of an open editor lives in `EventEditorModel` and `CalendarEditorModel`. New UI under `App/Editor/`, one responsibility per file.

**Tech Stack:** Swift (language mode 5), SwiftUI, EventKit, EventKitUI (iOS only), Swift Testing, XcodeGen, Xcode 26, iOS 26, macOS 26.

**Spec:** `docs/superpowers/specs/2026-11-17-daybook-design.md`, sections 3.1, 3.2, 4.2, 4.3 (rule 9), 4.6, 4.7, 5 and 6. This plan covers build step 3 of section 9.

**Scope notes for M3:**
- Categories in the editor and the detail (spec 4.6, 4.8) belong to M4. The read-only event's form is not shown at all in M3 (there is nothing editable on it until categories exist): the detail shows a lock and one line instead of Edit and Delete.
- The recurrence editor offers never, daily, weekly, monthly, yearly and an optional end date. A rule EventKit holds with more detail (every second week, on given weekdays) is shown by its frequency and interval and is left untouched by a save unless the user changes the recurrence.
- One alert per event is edited (the first). Further alerts on an event are kept untouched unless the alert is changed.
- The time zone is chosen from a short list (the device's zone, the event's zone, and common zones), not the full database: a 600-row menu is not usable, and a searchable list is not worth its cost before M5.
- Changing the recurrence of one occurrence is only offered as "this and future events", the way EventKit applies it.
- Double-click on an empty part of a month day creates a timed event (all-day off) on that day at the default hour; double-click in the time grid creates one at that time, snapped down to the half hour.
- Invitations: on iOS and iPadOS "Pozvat účastníky" saves the draft and opens `EKEventEditViewController`. In demo mode there is no system event, so the button explains that instead of opening anything. macOS shows attendees only.
- Debug demo arguments stage every new state for screenshots. Verification never touches the real calendar database: the app runs only with `-demo`.

**Conventions:** as in the M1 plan. Run package tests with `swift test --package-path Packages/DaybookCore`. Build with `xcodegen generate`, then `xcodebuild -project Daybook.xcodeproj -scheme Daybook -derivedDataPath .build/xcode -quiet build` with `-destination 'platform=macOS'` and `-destination 'generic/platform=iOS Simulator'`. Work on branch `m3-editing`.

### Task 2: Event drafts

**Files:**
- Create: `Packages/DaybookCore/Sources/DaybookCore/Edit/EventDraft.swift`
- Test: `Packages/DaybookCore/Tests/DaybookCoreTests/EventDraftTests.swift`

**Behaviour:** `EventDraft(event:calendar:)` copies the editable fields; for all-day events `start` and `end` are the first and last day. `problems(calendar:)` returns `endBeforeStart`, `recurrenceEndsBeforeStart`, `invalidURL`, `noCalendar`; an empty title is allowed. `setStart(_:calendar:)` keeps the duration (seconds for timed, days for all-day). `setAllDay(_:calendar:)`. `changeTimeZone(to:calendar:)` keeps the wall-clock times. `spanChoices(original:)`: none for a single event, only `futureEvents` when the recurrence changed, both otherwise. `EventDraft.newEvent(on:now:calendarID:calendar:)`: the focused day at the next full hour after `now`, one hour long, clamped to 23:00 of that day. `preferredCalendarID(writable:lastUsed:systemDefault:)`. `normalizedURL` adds `https://` when the scheme is missing.

- [ ] **Step 1: Write the failing tests**
  - draft from a timed event copies every field; from an all-day 3-day event has first and last day
  - empty title has no problems; end before start is `endBeforeStart`; equal start and end is fine
  - all-day draft whose last day is the first day is valid
  - recurrence end the day before the start is `recurrenceEndsBeforeStart`
  - `"example.com"` normalizes to `https://example.com`; `"exa mple"` is `invalidURL`; empty URL is fine
  - moving the start by 2 h moves the end by 2 h; moving an all-day start by a day keeps 3 days
  - switching all-day on lands on midnights; switching off gives 9:00 to 10:00 on the first day
  - changing 10:00 Prague to New York keeps 10:00 and moves the instant by 6 h
  - span choices for single / recurring unchanged / recurring with a changed rule
  - new event at 10:20 on the 17th starts at 11:00 and lasts one hour; at 10:00 starts at 11:00; for the 20th starts at 11:00 on the 20th; at 23:30 stays on the day at 23:00
  - DST: on 25 Oct 2026 at 01:30 the new event starts at 02:00 and ends one hour later; on 29 Mar 2026 at 01:10 the start is a real instant on the 29th and the end is one hour after it
  - preferred calendar: last used when writable, else system default when writable, else first writable, else `nil`
- [ ] **Step 2: Run** the tests. Expected: build fails, `cannot find 'EventDraft' in scope`.
- [ ] **Step 3: Implement. Step 4: Run.** Expected: all pass.

### Task 4: Writes in the in-memory store

**Files:**
- Modify: `Packages/DaybookCore/Sources/DaybookCore/Store/CalendarStore.swift`, `InMemoryCalendarStore.swift`
- Create: `Packages/DaybookCore/Sources/DaybookCore/Store/EventSeries.swift`
- Test: `InMemoryWriteTests.swift`, `RecurrenceTests.swift`

**Behaviour:** protocol gains `sources()`, `defaultCalendarID()`, `createEvent(_:)`, `updateEvent(_:with:span:)`, `deleteEvent(_:span:)`, `createCalendar(_:)`, `setColor(_:ofCalendar:)`. Writes validate the draft, refuse read-only and missing calendars with typed errors, and emit one change each. A draft with recurrence creates a series; `events(in:)` expands series. Only this event: an exception (changed occurrence, or a deleted one). This and future: from the first occurrence the whole series changes; from a later one the series ends the day before and a new series (or single event) starts from the draft. Deleting this and future from the first occurrence deletes the series.

- [ ] **Step 1: Write the failing tests**
  - create returns the event and it is found in its interval; created all-day event ends one second before the midnight after its last day
  - create in a read-only calendar throws `calendarReadOnly`; in a missing one `calendarNotFound`; an invalid draft throws `invalidDraft`
  - update changes title and times; moving to another calendar; update of an unknown event throws `eventNotFound`
  - delete removes the event
  - each write emits exactly one change
  - weekly series yields one occurrence a week, stops after its end day, keys share the external ID
  - monthly series from 31 Jan lands on the last day of shorter months
  - only this: retitled occurrence changes, neighbours keep the title; deleted occurrence disappears alone
  - this and future from the third occurrence: first two keep the old title, later ones have the new one; deleting this and future from the third keeps two
  - this and future from the first occurrence changes all; deleting removes all
  - turning a single event into a series; removing the recurrence from the whole series leaves one event
  - create a calendar in iCloud; refused in Google with `sourceDoesNotAllowCalendars`; colour change on a writable calendar, refused on a read-only one
- [ ] **Step 2: Run, see them fail. Step 3: implement. Step 4: run, see them pass.**
- [ ] **Step 5: Commit** `Implement event and calendar writes in the in-memory store`.
